# 法眼 · 法律知识库智能问答系统 —— 项目讲解

> 这份文档的目标：让一个没看过代码的人，20 分钟内理解这个项目做了什么、为什么这么做、
> 关键技术点在哪、以及被问到时该怎么讲。
>
> 全文分四部分：**Why（为什么做）→ What（做了什么）→ How（怎么实现）→ 取舍与局限**。

---

## 一、项目定位

### 1.1 一句话概括

一个面向中国现行法律的检索增强问答系统：用户用口语描述法律问题，系统先判断问题属于哪个
法律部门，检索对应的法条原文，再依据条文生成带出处的回答。

### 1.2 为什么选法律这个场景

做 RAG 项目最容易犯的错，是把"通用问答 + 向量库"包装成"行业解决方案"。法律场景不一样，
它对 RAG 的要求恰好长在通用方案的短板上：

| 法律场景的真实需求 | 通用 RAG 的做法 | 为什么不够 |
|---|---|---|
| 答案必须有出处，能核对到"第几条" | 返回一段相似文本 | 用户要的是条号，不是"大意相近的一段话" |
| 条号查询必须精确 | 向量检索 top-k | 向量会召回"相邻的几条"，未必是第 19 条 |
| 不能编造 | 让模型"根据资料回答" | 提示词约束不住幻觉，必须有结构化的兜底 |
| 口语问题要能映射到法言法语 | 直接用原问题检索 | "老板不给加班费" 检索不到"延长工作时间" |

也就是说，法律场景逼着你不能只做一个"向量库 + LLM"的 demo，必须认真处理
**精确性、可溯源性、查询改写**这三件事。这正是我想在这个项目里体现的能力。

### 1.3 目标用户与典型问题

- 普通劳动者：试用期、加班费、被辞退、工伤
- 消费者：七天无理由、假货赔偿、预付卡跑路
- 普通市民：离婚财产、遗产继承、租房押金
- 小微经营者：公司设立、股权转让、食品安全合规

问题形态分两类，这个区分贯穿整个设计：

- **A 类（确定性查询）**："劳动合同法第十九条怎么规定" —— 答案是唯一的
- **B 类（开放式咨询）**："公司不给我加班费怎么办" —— 需要理解、检索、组织

## 二、技术栈与选型理由

### 2.1 全景

```
┌──────────────────────────────────────────────────────────────┐
│  前端  Vue 3 (Composition API) + Vite + axios                │
│        自研 SSE 解析（fetch + ReadableStream）                │
├──────────────────────────────────────────────────────────────┤
│  接口  FastAPI（APIRouter）+ Pydantic 契约层                  │
│        StreamingResponse 实现 text/event-stream               │
├──────────────────────────────────────────────────────────────┤
│  业务  service 层：三段式编排（路由 → 检索 → 生成）            │
├──────────────────────────────────────────────────────────────┤
│  检索  Milvus Lite（向量）+ MySQL（结构化法条）+ 智谱 Rerank   │
├──────────────────────────────────────────────────────────────┤
│  模型  智谱 GLM（OpenAI 兼容协议），httpx 直连                 │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 逐项说明：选了谁，为什么，以及为什么不选另一个

#### 为什么最终选 FastAPI（附 Flask 版的取舍）

这个项目**先写了一版 Flask，再迁移到 FastAPI**，两个版本都跑通过。
保留这段经历是因为它比"直接选 FastAPI"更能说明问题。

**Flask 版当初的理由**：目标岗位技术栈以 Flask/Django 为主，用 Flask 写一遍
能讲清楚"怎么做分层、怎么做 SSE、怎么管数据库连接"。

**迁到 FastAPI 的理由**，只有一条但足够硬：

> 这个项目的核心特征是「长连接 + 长时间等待」—— 一次问答要挂 10—30 秒。

Flask 同步模型下，一个 SSE 连接占一个线程；10 个并发对话就是 10 个线程常驻，
100 个就是 100 个。FastAPI 的 async generator 挂在事件循环上，
协程开销只有几 MB，单机挂几百个连接没问题。

这不是"框架新不新"的问题，是**架构匹配度**的问题。

**迁移的实际代价**（不是"换个写法"那么简单）：

| 层 | 改动 | 说明 |
|---|---|---|
| `main.py` | 重写 | `lifespan` 替代 `before_request` + 标志位 |
| `api/` | 重写 | `Blueprint`→`APIRouter`，`request`→函数参数 |
| `schemas/` | **新增** | Pydantic 模型，顺带解决校验和文档 |
| `llm/client.py` | 加异步版 | **关键**：不加这个，SSE 并发模型和 Flask 一样，等于白改 |
| `service/` 两个文件 | 改 async | `stream_answer` / `sse_stream` 改异步生成器 |
| `dao/`、`rag/`、`config.py` | **0 改动** | 与框架无关，40 个文件里 28 个一行没动 |

**Flask 时代踩的坑，在 FastAPI 里依然存在**（只是换了个表现形式）：
Flask 的请求上下文在视图 return 后就回收，所以生成器内部不能用注入的 db session；
FastAPI 的 `yield` 依赖同样在响应开始发送时退出，所以 SSE 接口也不能用
`Depends(get_db)`。两边都得在生成器内部自己开 session —— 见
`service/chat_service.py` 的注释。

#### Milvus Lite 而不是 ChromaDB

原项目用 ChromaDB。换 Milvus 的理由：

1. **简历上更有分量**。Chroma 是"入门级"向量库，Milvus 是国内生产环境用得最多的
   向量数据库，提问者对这个名字的认可度更高。
2. **Milvus Lite 是嵌入式的**。`MilvusClient("./xxx.db")` 直接在当前进程里起库，
   不需要 Docker、不需要独立服务，数据落在一个目录里随项目走 —— 这解决了
   "现场演示时还要先起个容器"的尴尬。
3. **同一套 API 能平移到集群**。生产环境把 `MILVUS_URI` 从目录路径改成
   `http://host:19530`，代码一行不用动。这个"从 Lite 到 Standalone 的迁移路径"
   本身就是个可以讲的架构点。

> **踩坑记录**：Milvus Lite 在 Windows 上长期不被官方支持。我实测 `milvus-lite 3.2.2`
> 已经可以在 Windows 上跑（底层换成了 faiss-cpu），但 `pymilvus 3.x` 的
> `create_index` 签名变了 —— 从 `create_index(name, field_name, params)` 改成
> `create_index(name, IndexParams)`，网上大量 2.x 时代的教程在这版会直接报
> `ParamError: expected IndexParams`。这个坑我写在 `rag/milvus_store.py` 的注释里。

#### 智谱 GLM 而不是 OpenAI / DeepSeek

三个现实原因：国内网络直连稳定、embedding 和 rerank 能在同一个 key 下解决
（省一个供应商）、有免费额度。

技术上它兼容 OpenAI 协议，所以 `llm/client.py` 换 `base_url` + `model` 就能切到
DeepSeek / 通义。设置页的模型下拉就是干这个的。

#### 不用 LangChain / LlamaIndex

原项目基于 LlamaIndex。这次全部手写，理由：

1. **这一层的代码量本来就不大**。检索 = 向量化 + 查库 + 排序，一万行框架不如
   三百行自己写的代码好调试。
2. **框架的抽象会掩盖问题**。LlamaIndex 的 `QueryEngineTool` 把检索、重排、
   提示词拼装全包了，出了问题是"召回不准"还是"提示词不对"根本分不清。
   自己写之后，每一步都能单独打日志、单独测。
3. **版本兼容是真实痛点**。原项目就踩过 LlamaIndex 0.14 把 `ReActAgent.from_tools`
   改成 workflow API 的坑，整层重写。手写没有这个问题。

代价是要自己处理批量向量化的重试、维度校验、SSE 分帧这些脏活 —— 但这些恰恰是
最能体现工程能力的地方。

#### MySQL 而不是 PostgreSQL

没有技术上的强理由，就是国内中小团队更常见、运维更熟。这里用 MySQL 的场景很轻：
会话、消息、法条、文件台账、一行配置，没有复杂查询，没有 JSON 检索需求。

唯一值得一提的是**法条表的索引设计**：`(law_name, article_no)` 联合索引支撑
"某部法第几条"的精确查询，`(domain, article_index)` 支撑"按领域浏览/排序"。

## 三、系统架构

### 3.1 分层

```
┌─────────────────────────────────────────────────────────┐
│  api/          接口层：参数校验、HTTP 语义、SSE 帧格式    │
│                只做三件事：收参数 → 调 service → 包响应    │
├─────────────────────────────────────────────────────────┤
│  service/      业务层：编排、事务边界、降级策略            │
│                不碰 SQL，不碰 HTTP                        │
├─────────────────────────────────────────────────────────┤
│  dao/          数据层：SQLAlchemy 模型 + CRUD             │
│                只做数据存取，不含业务判断                  │
├─────────────────────────────────────────────────────────┤
│  rag/ llm/     能力层：检索、向量化、重排、模型调用        │
│                可独立测试，不依赖 Web 框架上下文            │
└─────────────────────────────────────────────────────────┘
```

为什么要分这么细：**为了能单独测**。

举个例子，"试用期最长多久"这个问题答错了，可能是：
- 路由判错了领域（判成 civil，去了民法典）
- 检索没召回劳动合同法第十九条
- 召回了但精排把它排到第 5 位，被截断
- 都对了，但提示词让模型自由发挥

分层之后，每一层都能单独验：直接调 `retrieve()` 看召回了什么，直接调
`route()` 看判成什么，直接看 `format_context()` 拼出来的上下文。不分层的话，
只能对着一个 500 错误猜。

### 3.2 一次问答的完整数据流

```
用户输入「公司不给我加班费怎么办」
   │
   ├─[1] POST /api/chat/stream  {session_id, query, use_rerank}
   │
   ├─[2] chat_service.sse_stream
   │      ├─ 开独立 db session（不能在视图里用注入的）
   │      ├─ 读 system_setting（当前模型、top_k、rerank_n）
   │      ├─ 取最近 6 条历史消息
   │      └─ 进入 agent_service.stream_answer
   │
   ├─[3] ① 路由（1 次 LLM 调用，temperature=0）
   │      ├─ 输出 JSON: {intent:"advice", domain:"labor", rewritten:"加班费 延长工作时间 加班工资 百分之一百五十"}
   │      └─ 失败则降级为规则路由（关键词表匹配）
   │
   ├─[4] ② 检索
   │      ├─ 第 1 路 结构化直查：query 里有「法名+条号」才触发
   │      ├─ 第 2 路 向量召回：law_labor 集合 top 8
   │      ├─ 第 3 路 词表扩展：「加班费」→「延长工作时间 加班工资 150%」再检索一次
   │      ├─ 三路合并 → 按 (score + 结构化偏置) 排序 → 取前 12
   │      └─ Rerank 精排 → 保留 4 条
   │
   ├─[5] ③ 生成（1 次 LLM 流式调用）
   │      ├─ 上下文按 [1][2][3] 编号注入
   │      ├─ 系统提示词约束：只能依据资料、必须标条号、不许编
   │      └─ 逐 token 通过 SSE 推给前端
   │
   └─[6] 落库：user 消息 + assistant 消息（含 sources JSON）+ 耗时
          SSE done 事件
```

关键点：**端到端只有 2 次 LLM 调用**。这个数字后面会反复用到。

## 四、知识库设计

### 4.1 语料构成

32 份 Markdown，按法律部门分六个目录：

| 目录 | 领域 | 份数 | 代表性法律 |
|---|---|---|---|
| `01_civil` | 民事法律 | 6 | 民法典总则/婚姻家庭/继承/合同/物权/侵权责任编 |
| `02_labor` | 劳动与社会保障 | 5 | 劳动合同法、劳动法、工伤保险条例、劳动争议调解仲裁法、社会保险法 |
| `03_criminal` | 刑事与治安 | 5 | 刑法总则、侵犯财产罪、危险驾驶与交通肇事、治安管理处罚法、刑事诉讼法 |
| `04_business` | 商事与经济 | 5 | 公司法、消费者权益保护法、食品安全法、产品质量法、个人所得税法 |
| `05_digital` | 数字与知识产权 | 5 | 著作权法、商标法、专利法、个人信息保护法、反电信网络诈骗法 |
| `06_procedure` | 程序与救济 | 6 | 民事诉讼法、诉讼时效与证据规则、行政复议法、行政处罚法、国家赔偿法、仲裁与法律援助 |

统计口径（实测）：**462 条结构化法条，845 条向量切片，约 12.7 万字**。

### 4.2 为什么按"法律部门"分集合，而不是一部法律一个集合

一部法律一个集合会有 32 个 collection，检索时要遍历 32 个、合并 32 组结果，
不仅慢，而且每部法律平均只有十几条法条，单集合内检索的区分度很低。

按部门分（6 个）的好处：

- 每个集合 100—230 条切片，检索区分度足够；
- 路由只需要在 6 个里选一个，准确率明显高于 32 选 1；
- 独立重建，改一部法律不用重跑全库。

### 4.3 文档格式约定（这是整个系统的地基）

每份 Markdown 必须遵循固定结构，解析器才能稳定提取法条：

```markdown
# 《中华人民共和国劳动合同法》核心条文与实务要点

> 法律名称：中华人民共和国劳动合同法
> 简称：劳动合同法
> 施行日期：2008-01-01
> 领域：labor
> 标签：书面劳动合同, 试用期, 经济补偿

## 一、适用范围与书面合同

（这一章的解释性文字，会被切成 passage 切片）

### 第十条 【建立劳动关系应当订立书面劳动合同】

建立劳动关系，应当订立书面劳动合同。
已建立劳动关系，未同时订立书面劳动合同的，应当自用工之日起一个月内订立书面劳动合同。

### 要点：什么是事实劳动关系

（以"要点："开头的小节，只进向量库，不进法条表）
```

解析规则（`rag/chunker.py`）：

| 行模式 | 处理 |
|---|---|
| `> key：value` | 文件头元信息，映射成 `law_name` / `law_short` / `effective_date` 等字段 |
| `## xxx` | 切换"章"，会写进后续 chunk 的前缀 |
| `### 第X条 【主旨】` | 开一个**法条小节**：进 MySQL 法条表 + 进向量库 |
| `### 要点：xxx` | 开一个**普通小节**：只进向量库 |
| 其他文本 | 段落缓冲，按句号切分后进向量库 |

### 4.4 结构感知切分：为什么不能按固定窗口切

通用做法是 `chunk_size=500, overlap=50` 硬切。放到法条上会出事：

```
原文：
  第十九条 【试用期期限】
  劳动合同期限三个月以上不满一年的，试用期不得超过一个月；
  劳动合同期限一年以上不满三年的，试用期不得超过二个月；
  ...

硬切之后 chunk 1 结尾："劳动合同期限一年以上不满三年的，试用期不得"
硬切之后 chunk 2 开头："超过二个月；三年以上固定期限..."
```

用户问"一年以上三年以下的合同试用期多久"，检索到 chunk 1 会得到一个残缺的答案，
检索到 chunk 2 则完全看不懂在说什么。

所以这里做的是：**一条法条 = 一个 chunk，绝不拆开**。只有法条之外的解读文字
才按句子边界滑动切分。

### 4.5 上下文前缀：提升召回最便宜的一招

每个 chunk 送去 embedding 之前，前面拼一段出处信息：

```
法条 chunk:  《劳动合同法》第十九条【试用期期限】（二、试用期）
             劳动合同期限三个月以上不满一年的，试用期不得超过一个月；...

普通 chunk:  《劳动合同法》二、实务问答 要点：什么是事实劳动关系
             没有书面合同，但同时具备下列情形的，劳动关系成立……
```

为什么有用：向量模型对"短查询 vs 长文档"的匹配天然吃亏。用户问
"劳动合同法第十九条"，文档里只有"劳动合同期限三个月以上..."，两者的语义距离
并不近。拼上出处之后，查询词和文档里出现了同样的关键词和条号，余弦相似度直接上去了。

这一招零成本（不增加 embedding 调用次数），但在这类"查询带明确实体名"的场景里
效果非常明显。

### 4.6 双索引：同一份源文件，两种检索形态

```
                  01_劳动合同法.md
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
      parse_markdown()        parse_markdown()
              │                     │
        chunks (26 条)        articles (24 条)
              │                     │
              ▼                     ▼
    embed → Milvus            INSERT MySQL
    law_labor 集合            statute_article 表
    （语义、模糊）             （条号、精确）
```

为什么要两份：

- 用户问"公司不给加班费" —— 只有向量检索能干活，MySQL 里搜"加班费"只能做 `LIKE`，
  召回的是包含这三个字的条文，不是语义相关的条文。
- 用户问"劳动合同法第十九条" —— 向量检索可能召回第十七、十八、二十条，
  但 MySQL 一条 `WHERE law_name LIKE '%劳动合同法%' AND article_no='第十九条'`
  就是 100% 准确。

两条路各管一段，在 `retriever.retrieve()` 里合并，这是整个检索层最核心的设计。

## 五、检索链路详解

### 5.1 三路召回

```python
# service 层伪代码
signals = detect_structured_signals(query)   # 抽「法名 + 条号」
candidates = []

# 第 1 路：结构化直查（精确）
if signals.article_no and signals.law_name:
    row = statute_dao.find_by_article(db, signals.law_name, signals.article_no)
    if row:
        candidates.append({... row ..., "score": 1.0, "source": "structured"})

# 第 2 路：向量检索（覆盖）
vector = embedder.embed_query(query)
for domain in domains:
    candidates.extend(milvus_store.search(f"law_{domain}", vector, top_k=per_domain))

# 第 3 路：词表扩展后的补召回
expanded = expand_query(query, domain)       # 「加班费」→「延长工作时间 加班工资 150%」
if expanded != query:
    for hit in milvus_store.search(..., embed(expanded), ...):
        hit["score"] *= 0.92                 # 扩展召回打 8% 折扣
        candidates.append(hit)
```

### 5.2 为什么要做词表扩展

用户的原话是口语，法条是法言法语，两者在向量空间里不一定近：

| 用户说法 | 法条用词 |
|---|---|
| 老板不给加班费 | 延长工作时间、支付不低于工资的百分之一百五十 |
| 被车撞了 | 机动车交通事故责任 |
| 公司把我开了 | 用人单位单方解除劳动合同 |
| 吃坏肚子 | 不符合食品安全标准 |

手写一张"口语 → 法言法语"的映射表（`retriever.DOMAIN_LEXICON`），命中就把
规范表述拼进查询再检索一次。零 LLM 成本、毫秒级，比"用 LLM 做 query 改写"
便宜得多。

**限制条件**：只在问题长度 ≤ 24 字时启用。长问题本身信息已经足够，再塞词反而
把语义拉偏。这是实测出来的阈值。

### 5.3 为什么扩展召回的分要打 92 折

扩展后的查询是"原问题 + 一堆法条术语"，它的向量已经偏离了用户的原始意图。
如果不打折，扩展召回的分数可能盖过原始查询的命中，把排序搞乱。

92% 这个数是经验值：足够让扩展召回进入候选池，又不至于顶掉原查询的前几名。

### 5.4 融合与精排

```python
merged = dedupe(candidates)                  # 按 (法名, 条号, 前40字) 去重
merged.sort(key=lambda h: h["score"] + (0.5 if h["source"] == "structured" else 0))
shortlist = merged[:max(rerank_n * 3, 12)]   # 送 12 条进精排

final = reranker.rerank(query, shortlist, top_n=rerank_n)   # 用原始 query，不是扩展后的

# 兜底：结构化直查的命中不能被精排挤掉
if structured and not any(s["source"] == "structured" for s in final):
    final = structured[:1] + final[:rerank_n - 1]
```

三个细节值得说：

1. **去重键包含前 40 字**。同一部法律的同一条可能被三路都召回，
   纯按 `(法名, 条号)` 去重会把不同版本的条文（比如修正前后）误合并。
2. **结构化命中加 0.5 偏置**。直查命中的分数是 1.0，但向量分最高也是 1.0，
   加偏置是为了确保它排在候选池最前面，一定进精排。
3. **精排用原始 query**。扩展后的 query 里有大量法条术语，用它做精排会让
   reranker 偏向"术语多"的文档，而不是"真正回答用户问题"的文档。

### 5.5 为什么要 Reranker

向量检索是双塔模型：问题和文档各自独立编码，最后算余弦。它快，但问题和文档之间
没有细粒度交互。Reranker 是交叉编码器，把 `(问题, 文档)` 拼起来过一遍模型，
能判断"这段话到底有没有回答问题"。

法律场景的典型例子：

```
问题：试用期最长能约定多久？
粗排 top 3：
  [1] 第二十条【试用期工资】劳动者在试用期的工资不得低于……   0.82
  [2] 第十九条【试用期期限】劳动合同期限三个月以上……不得超过六个月  0.79
  [3] 第二十一条【试用期解除】在试用期中，除劳动者有……         0.76
```

三条都含"试用期"，向量分很接近。但只有第 2 条回答了"多久"。Rerank 之后
第 2 条的分数会明显拉开。

代价是延迟（+300~600ms）和费用。所以做成可开关（前端顶栏"精排"开关），
并且**失败即降级**：接口超时或报错就退回向量分，不让整条链路挂掉。

### 5.6 检索参数与实测

| 参数 | 默认值 | 说明 |
|---|---|---|
| `top_k` | 8 | 每个领域的向量召回条数 |
| `rerank_n` | 4 | 精排后保留条数 |
| 跨域时每域召回 | `max(2, top_k // 2)` | 6 个域 × 4 条 = 24 条候选，控制 rerank 成本 |
| `CHUNK_SIZE` | 420 | 普通段落切分长度 |
| `CHUNK_OVERLAP` | 60 | 段落切分重叠 |

## 六、Agent 编排：为什么不用自由 ReAct

### 6.1 ReAct 的代价

ReAct 的链路是：思考 → 调工具 → 观察 → 再思考 → 再调工具 → 回答。
在法律问答里这套东西有三个问题：

1. **慢**。每多一轮就多一次完整 LLM 调用。原项目实测一次复杂问答要 8—15 秒。
2. **贵**。法律问题往往需要多轮工具调用，token 消耗是固定链路的 3—5 倍。
3. **不稳定**。通用模型对"该查劳动合同法还是民法典"的判断本来就不稳，
   让它自由探索反而容易绕圈，甚至同一个问题两次路由到不同领域。

### 6.2 三段式的思路

```
① Router   1 次 LLM：意图分类 + 领域锁定 + 查询改写
② Retrieve 0 次 LLM：三路召回 + 精排
③ Generate 1 次 LLM：带编号上下文的流式生成
```

本质仍然是 Agent 的决策链 —— 有意图判断、有策略选择（走结构化还是走向量）、
有降级路径。只是把"自由探索"换成了"固定但可解释的编排"。

**收益**：
- 链路开销从 8—15 秒降到 2—4 秒，且方差小（可预测）
- 成本固定 2 次调用，可以按 QPS 估费
- 每一段都能单独打日志、单独测、单独优化

### 6.3 路由的两个细节

**细节一：明显是法条查询时跳过 LLM 路由**

```python
rule = _rule_route(query)
if not allow_llm or (rule["intent"] == "statute" and rule["domain"] != "all"):
    return rule      # 省掉一次 ~1.5 秒的 LLM 调用
```

问题里出现"第X条"或书名号法律名，这是确定性极高的信号，没必要花钱让模型再判一遍。

**细节二：LLM 路由必须有规则兜底**

模型超时、返回非 JSON、返回的 domain 不在注册表里 —— 任何一种情况都退回关键词表
（`DOMAIN_KEYWORDS`）。规则路由的准确率不如 LLM，但它不会挂。

这体现一个原则：**LLM 是增强项，不是单点依赖**。模型服务挂了，系统应该降级成
"规则路由 + 向量检索"，而不是整个不可用。

### 6.4 严格模式

`system_setting.strict_mode` 控制提示词强度。开启时：

```
1. 必须以【参考资料】中的法条为依据，每引用一条都要写明《法律名称》第X条。
2. 参考资料里没有的内容，绝对不要凭空编造法条、条号或司法解释。
3. 区分三类内容：法律规定 / 实务理解 / 行动建议。
4. 涉及金额、期限、比例的，给出具体数字和计算方式。
5. 不夸大、不承诺结果。
```

检索结果为空时，换成另一套提示词：明确告诉用户"知识库暂未检索到直接对应的法条"，
基于常识给方向性建议，但要标注"（非条文原文，供参考）"，并引导用户补充信息。

**这是法律场景和通用聊天最大的区别**：宁可说"我不知道"，也不能编一条假法条。

### 7.1 为什么 sources 要落库

原项目的注释写着"溯源不落库，避免表膨胀"。这次改成落库，理由是体验：
用户刷新页面回看历史对话时，如果法条出处没了，"可溯源"这个卖点就打了折扣。

代价是每行 assistant 消息多存 1—2 KB JSON。以 1 万条消息算，约 20 MB，可以接受。

### 7.2 knowledge_doc 表的作用

存文件内容 sha1。重建索引时：

```python
if not force and record and record.file_hash == fingerprint:
    return IndexResult(..., skipped=True, reason="文件未变化，跳过")
```

32 份文档全量重跑要花几分钟和一笔 embedding 费用。有了这张表，
改一份文件只重建一份。这是实打实的成本优化，不是纸面设计。

### 7.3 为什么用 `session_id` 做字符串主键而不是自增

前端首次发消息时自己生成 `s_<timestamp>_<random>`，后端 `get_or_create`。
好处是不需要"先调接口建会话再发消息"两步，少一次往返，也不会出现
"建了会话但没发消息"的空记录。

## 八、关键工程细节

### 8.1 SSE：生成器内部必须自己管 session

```python
def sse_stream(session_id, query, use_rerank):
    db = SessionLocal()        # ← 关键：不在视图里用 Depends 注入的 db
    try:
        ...
        for event in agent_service.stream_answer(db, cfg, query, ...):
            yield _sse(event)
    finally:
        db.close()
```

Flask 的 `teardown_appcontext` 在视图函数 return 时就执行了，此时流式响应还没
开始往外吐数据；FastAPI 的 `yield` 依赖同理，在响应开始发送时就会执行 `finally` 里的
close。两边都必须绕开依赖注入，在生成器里自己开 session。如果用注入的 session，会在生成到一半时报
`This session is in 'prepared' state` 或 `MySQL server has gone away`。

这个坑不写出来，下一个接手的人一定会踩。

### 8.2 前端 SSE：为什么不用 axios

axios 基于 XHR，拿不到"边下边读"的增量数据。只有 `fetch` + `ReadableStream`
才能真正一帧一帧读 SSE。

`src/api/stream.js` 手写了一个解析器：

```js
buffer += decoder.decode(value, { stream: true }).replace(/\r\n/g, '\n')
while ((index = buffer.indexOf('\n\n')) !== -1) {
  const frame = buffer.slice(0, index)
  buffer = buffer.slice(index + 2)
  const dataLine = frame.split('\n').find(l => l.startsWith('data:'))
  handlers.onEvent?.(JSON.parse(dataLine.slice(5).trim()))
}
```

三个细节：`replace(/\r\n/g, '\n')` 处理 Windows 换行；`{ stream: true }`
处理多字节汉字被切断在 chunk 边界的情况；按 `\n\n` 分帧而不是按行分帧。

### 8.3 记忆：MySQL 全量 + 内存滑窗

```
MySQL chat_message      ← 全量历史，断电重启都在
        │
        ├─ 取最近 6 条 → 拼进 prompt 的 messages
        │
        └─ 取最近 20 条 → ChatMemoryBuffer（token_limit=4096）
```

为什么只给模型 6 条：法律问答里太早的上下文基本是干扰，而且会让模型把
上一件事的细节套到这一件上（比如上一个问题问离婚，这一个问工伤，
模型可能受"夫妻"影响）。6 条≈3 轮，够消解指代，不会引入噪声。

### 8.4 增量索引

```
读文件 → 算 sha1 → 与 knowledge_doc.file_hash 比对
                          │
                ┌─────────┴─────────┐
             相同                  不同
                │                    │
            直接跳过          删旧切片 → 向量化 → upsert → 更新台账
```

`chunk_id` 用 `sha1(domain::filename::seq)` 而不是 uuid4，保证同一条内容每次
重建得到同一个 id，Milvus 的 upsert 就会覆盖而不是重复追加。

### 8.5 降级矩阵

| 故障 | 表现 | 系统行为 |
|---|---|---|
| Reranker 超时/报错 | 精排不可用 | 退回向量粗排结果，日志记 warning |
| LLM 路由失败 | 拿不到 JSON | 退回关键词规则路由 |
| 检索为空 | 没召回到条文 | 换"无资料"提示词，明确告知未检索到，给方向性建议 |
| MySQL 连不上 | 启动报错 | 服务仍然拉起，接口返回明确的连接错误，前端能看到原因 |
| Milvus 集合不存在 | 检索报错 | `search()` 返回空列表，不抛异常 |
| Embedding 429/5xx | 向量化失败 | 指数退避重试 3 次（2s/4s/8s），仍失败才抛 |
| 用户点"停止生成" | 客户端断开 | 捕获 `GeneratorExit`，把已生成部分落库并标注 |

核心原则：**局部故障不能放大成整体不可用**。

### 8.6 密钥处理

三层保护：

1. `.env` 存明文，`.gitignore` 排除，仓库里只有 `.env.example`；
2. 接口返回永远脱敏（`c30bbq********h7k2`），浏览器拿不到明文；
3. 保存设置时 `api_key` 留空 = 沿用旧值，避免"打开设置直接保存"把 Key 清空。

补一条：`dao/setting_dao.py` 里还有一层兜底 —— 如果数据库里 key 被存成了空字符串，
自动回退到 `.env` 的值。

### 8.7 推理型模型：三个坑，一个比一个深

设置页支持切到 `glm-5.3-flash` 这类推理型模型。它能用，但接入过程踩了一串坑，
值得单独记一笔 —— 因为这几乎是所有"支持多模型切换"的项目都会遇到的事。

**坑一：思维链和正文是两个字段，不能混**

推理模型的响应长这样：

```json
{
  "message": {
    "reasoning_content": "The user is asking about... Let me check the materials... 
                           Note: I should not fabricate article numbers... 
                           Let me draft: 结论：公司安排加班不付加班费是违法的…",
    "content": "**结论**：公司的做法违法，你有权要求补发加班费…"
  }
}
```

`reasoning_content` 是草稿，`content` 才是答案。我最初的兜底逻辑写的是
"content 为空就取 reasoning_content"，想着"总比什么都不返回好"。

结果很惨：用户看到整段英文独白，里面有 "The user is asking"、"Let me draft"、
"注意要控制在500字以内"这种自我提醒。这不是"回答凌乱"，这是**把草稿直接印在了答题纸上**。

现在的处理：**绝不回退**。content 为空就明确告诉用户发生了什么、怎么改。

**坑二：思考过程会吃掉全部 token 预算**

实测 `glm-5.3-flash` 回答一个简单法律问题，思考部分 1000—1300 字符，
正文只有 50 字。复杂问题思考能到 3000 字符（约 2000 token）。

我原来的 `max_tokens=1600` 是按普通模型定的（正文 400—600 字够用）。
换成推理模型后，1600 被思考吃光，`content` 直接是空的 —— 这正好触发了坑一的兜底，
于是输出了一整段英文草稿。

现在的处理：按模型类型给预算，普通模型 1600，推理模型 4096。

**坑三：脏数据会自我复制**

最麻烦的是第三步。泄漏出去的思维链被存进了 MySQL，下一轮作为 assistant 历史
喂回模型。模型看到"自己"是这么说话的，就继续用英文思考、还开始"自我纠正"
（"Note: The previous conversation included some fabricated references"），
会话越聊越乱，而且看起来像是模型"变笨了"。

现在的处理是两层：

1. 源头堵住（不再把 reasoning 写进 content）；
2. 读时过滤 —— `message_dao.recent_for_memory` 会跳过疑似思维链的历史消息
   （长度 > 300 且含 `The user is asking` 等特征短语，或英文占比 > 40%）。

用"读时过滤"而不是"批量改数据库"，是因为已经污染的记录前端仍能展示，
用户自己能看见发生了什么，但不会再喂给模型。

**结论：法律问答不建议用推理模型。**

它擅长多步推理，而这个场景的难点在"检索准不准"，不在"想得深不深"。
实测同一个问题：

| 模型 | 首字延迟 | 总耗时 | 英文占比 |
|---|---|---|---|
| glm-4-flash | 6—12 s | 15—19 s | 0% |
| glm-5.3-flash | 18.8 s | 26 s | 0%（修复后） |

推理模型的思考过程对用户不可见，纯属额外等待。

### 8.8 连接池

```python
engine = create_engine(
    settings.mysql_url,
    pool_pre_ping=True,   # 取连接前先探活
    pool_recycle=1800,    # 提前回收，比 MySQL wait_timeout 激进

```

`pool_pre_ping` 解决"隔夜回来第一枪报 2013 Lost connection"，
`pool_recycle` 是双保险。这两个参数在长时间不活动的开发环境里几乎是必需的。

## 九、前端设计

### 9.1 状态管理：不用 Pinia

```js
export const state = reactive({ view, sessions, messages, ... })
export async function sendMessage(text) { ... }
```

这个应用的状态边界很清楚：会话、对话流、知识库、设置。一个 `reactive` 对象
加一组导出函数就够了，少一个依赖、少一层心智负担。

如果是多人协作、状态多到几百个字段，那该上 Pinia。现在的规模上 Pinia 属于过度设计。

## 十、性能与成本

### 10.1 一次问答的耗时构成（实测）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 路由（LLM，非流式，max_tokens=400） | 800—1500 ms | ~25% |
| 向量化查询（embedding-2） | 150—300 ms | ~5% |
| Milvus 检索（6 域 FLAT） | 20—40 ms | ~1% |
| Rerank 精排（12 → 4） | 300—600 ms | ~12% |
| 生成（流式，首字） | 700—1200 ms | ~20% |
| 生成（流式，全部完成） | 2000—4000 ms | ~40% |

链路固定开销 **2—4 秒**（路由 + 检索 + 精排），首字延迟 **6—12 秒**，
端到端 **15—25 秒**。

> 为什么端到端这么长：瓶颈在模型生成，不在链路。`glm-4-flash` 输出 400 字
> 要 10—15 秒，这部分不受我的工程设计影响。能优化的是前面那 2—4 秒 ——
> 比如"第X条"这类明确查询会跳过 LLM 路由，直接走规则，省掉 1.5—3 秒。

如果跳过 LLM 路由（问题里带条号），能再省 1—1.5 秒。

### 10.2 成本估算

一次问答：
- 路由：约 600 input + 150 output tokens
- 生成：约 2500 input（含 4 条法条上下文）+ 600 output tokens

按 GLM-4-Flash 的价格（约 0.1 元/百万 token 量级），单次问答成本在
**0.0005 元以内**。embedding 只在建索引时消耗，842 条切片一次性约 0.02 元。

也就是说，这个项目的运行成本基本可以忽略。真正的成本是建索引那几分钟。

### 10.3 建索引耗时

32 份文档 / 845 条切片 / 27 批 embedding 调用，实测 **8—12 分钟**（取决于接口
响应速度和是否触发限流重试）。

之所以不放在应用启动时自动跑：这是"一次性、有成本"的操作，必须由人显式触发。
每次重启偷偷跑一遍，既费钱又拖慢启动。`init_knowledge.py --build` 是显式命令，
不传参数只做建表和数据检查。

## 十一、已知局限与后续优化

写这一节不是为了凑数，是因为被问到时几乎一定会被问"你这个方案有什么问题"。
主动说出来，比被问出来好。

### 11.1 语料规模与时效

- 32 份文档覆盖的是"最常见"的法律问题，不是全量法律体系（现行有效法律近 300 部）。
- 条文以编写时的公开文本为准，修正案（如刑法修正案十二）可能未完全同步。
- **改进方向**：接入国家法律法规数据库的开放数据，做一个增量同步任务；
  在法条表加 `invalid_date` 字段，回答时提示"该条已修订"。

### 11.2 检索的固有短板

- 纯向量检索对**否定句**和**数字条件**不敏感。"不是工伤"和"是工伤"在向量空间
  里非常接近。
- 跨法条推理弱。比如"公司没交社保，我被迫离职能拿多少补偿"需要同时用到
  劳动合同法第 38 条、第 46 条、第 47 条，当前是分别召回，靠模型自己串。
- **改进方向**：引入 BM25 稀疏检索做混合召回（Milvus 支持 sparse vector），
  用 RRF 融合；对多法条问题做"子问题拆解 → 分别检索 → 合并上下文"。

### 11.3 路由的准确率上限

关键词表覆盖不到的表达会走 LLM 路由，而 LLM 路由有 1.5 秒延迟和 JSON 解析风险。
真正的生产系统应该在中间加一层小模型分类器（几百毫秒、准确率接近大模型）。

### 11.4 单机限制

- Milvus Lite 是进程内数据库，**单进程独占**：后端在跑时，`init_knowledge.py` 打不开
  同一个数据目录（会抛 `DataDirLockedError`），必须先停后端。同理 `app.run(use_reloader=False)`
  也是因为这个 —— reloader 会起两个进程，第二个抢不到库锁。
- 开发服务器不适合生产。FastAPI 用 `uvicorn --workers N`，但**多 worker 之前
  必须先把 Milvus Lite 换成 Standalone** —— 每个 worker 是独立进程，
  会抢同一个库锁。
- **改进方向**：向量库切 Milvus Standalone（改一个 URI），后端切 gunicorn，
  加 Redis 做会话级限流。

### 11.5 没有做的功能

诚实列出来，避免被问到时被问穿：

- 多轮对话中的**指代消解只靠提示词**，没有专门的 coreference 模型。
  "那工伤呢"这种追问，靠路由改写来补全，效果一般。
- **没有流式输出法条卡片**。检索完成就一次性推 `sources`，不是边生成边推。
- **没有用户体系**。所有人共用一个会话空间，靠 `session_id` 区分。
- **没有评测集**。这是最大的欠缺 —— 没有量化的召回率/准确率，所有优化都是
  靠人工看几个 case 判断的。

### 11.6 如果继续做，优先级排序

1. **建评测集**（100 条问题 + 标准答案 + 应召回的条号），把召回率、MRR 跑出来。
   没有度量就没有优化，这是第一优先级。
2. 混合检索（BM25 + 向量 + RRF）。
3. 多法条问题的子问题拆解。
4. 法条时效性管理（修订/废止标记）。
5. 用户体系与权限。
