# LlamaIndex 接入说明（文档解析层）

> 一句话：**只借它的 reader 把 PDF / Word 转成文本，切分和检索仍走自研链路。**

---

## 一、接了什么，没接什么

```
┌─────────────────────────────────────────────────────┐
│  文件（.md / .txt / .pdf / .docx）                   │
└────────────────┬────────────────────────────────────┘
                 │
      ┌──────────▼───────────┐
      │  LlamaIndex reader    │  ← 只在这一个环节用
      │  PDFReader / DocxReader│
      └──────────┬───────────┘
                 │ 纯文本
      ┌──────────▼───────────┐
      │  自己的切分器          │  ← chunker / doc_loader
      │  结构感知 / 段落聚合    │
      └──────────┬───────────┘
                 │ Chunk 列表
      ┌──────────▼───────────┐
      │  Milvus + MySQL       │  ← 自己的双索引
      └──────────┬───────────┘
                 │
      ┌──────────▼───────────┐
      │  三路召回 + RRF + 精排 │  ← 自研检索链路
      └──────────────────────┘
```

**没用** LlamaIndex 的 `VectorStoreIndex`、`QueryEngine`、`Retriever`、`NodeParser`。

原因有两条：

1. 本项目需要**双索引**（MySQL 精确查条 + 向量），框架的索引层是单向量的
2. 三路召回 + RRF 融合 + 结构化命中强制置顶，是针对性调出来的排序策略，框架的融合器表达不了

而"把 PDF 变成干净文本"这件事，它的 reader 确实比手写强：版式分析、表格抽取、编码处理。

---

## 二、支持哪些格式

| 格式 | 解析方式 | 切分方式 | 能进法条表 |
|---|---|---|---|
| `.md` / `.txt` | 直接读 | `parse_markdown`，按 `### 第X条` 边界 | ✅ 有结构就能 |
| `.pdf` | `llama_index.readers.file.PDFReader` | `parse_plain_text`，按段落聚合 | ❌ |
| `.docx` | `llama_index.readers.file.DocxReader` | 同上 | ❌ |

**PDF / DOCX 为什么不进法条表**：提取出来的是无结构文本流，
「第X条」的边界不可靠 —— 强行解析只会产生脏数据（条号错位、正文截断）。
它们作为补充语料只进向量库。

---

## 三、代码在哪

| 文件 | 作用 |
|---|---|
| `backend/rag/doc_loader.py` | 全部逻辑：`load_text()` + `parse_plain_text()` |
| `backend/service/knowledge_service.py` | `index_upload()` 按扩展名分流 |
| `backend/config.py` | `ALLOWED_SUFFIXES` 白名单 |
| `frontend/src/components/KnowledgeView.vue` | 上传 `accept` 与校验 |

### 关键函数

```python
# 文件 → 纯文本（唯一使用 LlamaIndex 的地方）
text = load_text(Path("合同.pdf"))

# 纯文本 → chunk 列表（自己的逻辑）
chunks = parse_plain_text(text, domain="upload", filename="合同.pdf")
```

`load_text` 做了三件容错：

1. **大小限制**：超过 20 MB 直接拒，PDF 解析很吃内存
2. **扫描件识别**：提取不出文字时提示"需要 OCR"，而不是返回空字符串
3. **页码清洗**：去掉每页底部的 `- 12 -` 这类行，压掉多余空行

`parse_plain_text` 的关键在"按段落块聚合"：

> PDF 提取的段落短的只有十几个字（表格单元格、列表项），
> 一段一个 chunk 会产生大量碎片，向量检索时语义不完整。
> 所以先累积到接近 `CHUNK_SIZE`（420 字）再切。

## 五、一个已知限制（要清楚）

**上传的文件进独立集合 `law_upload`，对话检索查不到。**

这是原有的设计（物理隔离，避免用户上传的杂乱内容和法律库混在一起），
不是这次改动引入的。所以现在的行为是：

- 知识库管理页能看到上传的文件、切片数
- **但对话里问相关问题，召回的是法律库的内容，不会用你上传的文档**

如果要做"文档问答"，需要改 `rag/retriever.py`，把 `law_upload` 也纳入检索范围。
两种做法：

1. **全量纳入**：`domains` 里加上 `law_upload`，所有对话都能检索上传内容 —— 简单，但可能污染法律问答
2. **场景开关**：前端加一个"文档问答"模式，只有这个模式查 `law_upload` —— 干净，但要改前端

目前没做，按需再定。

## 六、怎么解释这些设计

被问"你用过 LlamaIndex 吗"：

> 用过，但只在文档解析这一层。
>
> 我的项目需要双索引 —— 向量检索负责口语问题，MySQL 精确查条负责"第X条"这种明确查询。
> LlamaIndex 的索引层是单向量的，接不住这个结构；三路召回 + RRF 融合的排序策略，
> 它的融合器也表达不了。所以检索链路自己写。
>
> 但 PDF 解析我不打算自己造轮子 —— 版式分析、表格抽取这些是它的强项。
> 所以职责划得很清楚：**它负责「文件 → 文本」，我负责「文本 → 切片 → 检索 → 生成」**。
>
> 这也是我判断"什么时候该用框架"的标准：它强的地方用，它挡住你的地方不用。

**追问"那你了解 LlamaIndex 的核心概念吗"**：

> 了解。核心是 `Document` → `Node` → `Index` → `Retriever` → `QueryEngine` 这条链。
> 我这个项目只用到最前面的 `Document`（reader 的返回值），
> 后面的 `Index` 和 `QueryEngine` 我用自己的实现替代了。
>
> 如果要做一个标准的文档问答 demo，我会直接用 `VectorStoreIndex.from_documents()`
> 加 `as_query_engine()`，三行搞定。但我这个场景不行，原因就是上面说的双索引。

这个回答的好处：既证明用过，又证明知道为什么不用全部 —— 后者更值钱。
