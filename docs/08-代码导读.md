### 1.2 一次问答的完整调用链

这是整个项目最重要的一张图，**要能默画出来**：

```
浏览器 POST /api/chat/stream  {session_id, query, use_rerank}
   │
   ▼
① api/chat_api.py  chat_stream()
   │  · Pydantic 自动校验（query 非空、≤2000 字）
   │  · ⚠️ 这里没有 Depends(get_db)，见 3.2 的解释
   ▼
② return StreamingResponse(chat_service.sse_stream(...))
   │  ← 视图函数在这里就 return 了，但响应体才开始迭代
   ▼
③ service/chat_service.py  sse_stream()   [async generator]
   │  · 自己开 db session（不能靠依赖注入）
   │  · 读配置、建会话、取最近 6 条历史
   ▼
④ service/agent_service.py  stream_answer()   [async generator]
   │
   ├─ ① 路由 route()
   │     · 规则先跑（正则抓"第X条" + 书名号法名）
   │     · 命中就不调 LLM，省 1.5—3 秒
   │     · 否则 await llm.achat() 让它输出 {intent, domain, rewritten}
   │
   ├─ ② 检索 retrieve()   ← 包在 asyncio.to_thread 里
   │     · 第 1 路：结构化直查（MySQL 精确查条号）
   │     · 第 2 路：向量检索（6 个集合分别 search）
   │     · 第 3 路：词表扩展补召回（"加班费"→"延长工作时间"）
   │     · 去重 → 排序 → 精排 rerank → 兜底
   │
   └─ ③ 生成 astream_chat()   [async generator]
         · 拼上下文（format_context）
         · 拼 messages（system + 历史 + 当前问题）
         · 流式吐 token
   │
   │  期间不断 yield 事件：status / sources / delta / answer
   ▼
⑤ chat_service 把每个事件包成 SSE 帧 "data: {...}\n\n"
   │  · delta 时逐字累积（断线保存的前提）
   │  · answer 时落库 + yield done
   ▼
⑥ 浏览器：ReadableStream 逐帧解析 → 更新界面
```

**记住这条链上的四个"边界"**：

| 边界 | 为什么重要 |
|---|---|
| 视图 return vs 响应迭代 | Flask/FastAPI 的请求上下文都在 return 时回收，生成器里必须自己管资源 |
| 同步 vs 异步 | 异步链必须打通，中间混一个同步调用就卡死事件循环 |
| 函数调用 vs 线程池 | 检索和 DB 是同步的，必须 `asyncio.to_thread` 包起来 |
| 事件 vs 帧 | service 层产出 dict 事件，只有 api/chat_service 才管 SSE 格式 |

## 二、启动：从 `python main.py` 到服务就绪

### 2.1 lifespan：启动钩子

```python
# main.py
@asynccontextmanager
async def lifespan(app: FastAPI):
    logger.info("正在执行启动自检…")
    try:
        ensure_database()          # MySQL 库不存在就 CREATE DATABASE
        create_tables()            # 五张表不存在就建
        with session_scope() as db:
            total = statute_dao.count_all(db)
        logger.info("启动自检完成，法条表共 %d 条", total)

        vectors = sum(milvus_store.count(collection_name(k)) for k in LAW_DOMAINS)
        if vectors == 0:
            logger.warning("向量库为空，请先运行：python init_knowledge.py --build")
    except Exception as exc:
        # 关键：数据库没起来也把服务拉起来，让前端能看到明确报错，而不是白屏
        logger.error("启动自检失败：%s", exc)

    yield          # ← 服务从这里开始对外提供

    logger.info("服务关闭，释放资源")
```

💡 **常见疑问**：为什么不用 `@app.on_event("startup")`？

> 那个 API 在 FastAPI 0.109 之后就废弃了，官方推荐 `lifespan`。
> 而且 lifespan 能保证"启动和关闭成对出现"，`yield` 之前的代码一定在服务就绪前跑完，
> `yield` 之后的代码一定在进程退出前跑完，适合做资源释放。
>
> 迁过来之前的 Flask 版没有真正的启动钩子，我用 `before_request` + 一个标志位模拟的，
> 那是 workaround。lifespan 是原生支持。

### 2.2 路由注册与异常处理

```python
# api/__init__.py
def register_routers(app: FastAPI) -> None:
    from api import chat_api, knowledge_api, session_api, settings_api, statute_api, system_api
    for module in (chat_api, session_api, statute_api, knowledge_api, settings_api, system_api):
        app.include_router(module.router)
```

**为什么在函数内 import？** 避免循环导入 —— `api.chat_api` 会 import `schemas`，
`schemas` 不 import `api`，所以其实没有循环。但集中在一个地方 import，
好处是"新增模块只改这一个文件"，不会出现"写了接口忘了注册"。

异常处理注册了四个 handler：

```python
@app.exception_handler(BizError)                  # 业务错误，原样返回
@app.exception_handler(RequestValidationError)    # Pydantic 校验失败 → 压成 400 + 人话
@app.exception_handler(StarletteHTTPException)    # 404 / 405
@app.exception_handler(Exception)                 # 兜底，打堆栈 + 只说一句概括
```

💡 **`RequestValidationError` 那个 handler 是必须的**，可能会问：

> FastAPI 校验失败默认返回 422，结构是 `{"detail": [{...}]}`。
> 但前端拦截器是按 `{code, message, data}` 解析的，看到没有 `code` 字段
> 会当成成功响应放过去 —— 表现就是"明明报错了，界面却显示成功"。
> 所以我把 422 压成 400 + 中文提示，保持和业务错误同一个信封。

## 三、请求进入：api 层

### 3.1 一个完整接口的解剖

```python
# api/chat_api.py
@router.post("/stream", summary="流式对话（SSE）", response_class=StreamingResponse)
async def chat_stream(payload: ChatRequest):
    return StreamingResponse(
        chat_service.sse_stream(payload.session_id, payload.query, payload.use_rerank),
        media_type="text/event-stream; charset=utf-8",
        headers=SSE_HEADERS,
    )
```

**只有三行有效代码**，但它做完了四件事：
1. `payload: ChatRequest` —— Pydantic 自动解析 + 校验 + 生成文档
2. `async def` —— 因为要返回一个异步生成器
3. `StreamingResponse` —— 把生成器包装成流式 HTTP 响应
4. `headers` —— 关掉各级缓冲

`SSE_HEADERS` 的三个头，缺一个都可能有坑：

```python
SSE_HEADERS = {
    "Cache-Control": "no-cache, no-transform",  # 禁止代理缓存/转换
    "Connection": "keep-alive",                  # HTTP/1.1 长连接
    "X-Accel-Buffering": "no",                   # 让 Nginx 不要攒批
}
```

💡 **如果漏了 `X-Accel-Buffering`**：本地开发看不出问题，一上 Nginx 就会
"打字机效果消失，等 5 秒一次性出现"——因为 Nginx 默认会缓冲响应。

### 3.2 依赖注入：为什么 SSE 接口不能用 `Depends(get_db)`

这是这个项目最反直觉的一个点。

```python
# api/deps.py
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db          # ← 路由函数执行期间
    finally:
        db.close()        # ← 响应结束后清理
```

看起来没问题。但 **`StreamingResponse` 的生成器是在 `yield db` 之后才开始迭代的**：

```
视图函数执行 → return StreamingResponse(gen) → 依赖的 finally 执行 → db.close()
                                                        ↓
                                              这时 gen 才开始跑
                                                        ↓
                                              gen 里用 db → 报错
```

具体报什么取决于驱动，常见的是 `This session is in 'prepared' state` 或
`MySQL server has gone away`。

**所以 `chat_service.sse_stream` 里是这么写的**：

```python
async def sse_stream(session_id, query, use_rerank=None, direct=False):
    db = SessionLocal()        # ← 自己开
    try:
        ...
    finally:
        db.close()             # ← 自己关
```

💡 **可能会问**："Flask 版也是这样吗？"

> 是。Flask 的 `teardown_appcontext` 同样在视图 return 时就执行了。
> 所以这个坑跟框架无关，是"流式响应 + 请求级资源管理"的通用冲突。
> 两个版本的解法一样：生成器内部自己管 session。

### 3.3 其他接口为什么用 `def` 而不是 `async def`

```python
# api/session_api.py
@router.get("", response_model=ApiResponse[list[SessionInfo]])
def list_sessions(keyword: str = Query(default=""), db: Session = Depends(get_db)):
    return Result.ok(session_service.list_sessions(db, keyword, limit))
```

**没有 `async`**。因为这条路全是同步 DB 操作，没有 `await` 可写。

FastAPI 看到 `def`（不是 `async def`）会自动把整个函数丢进线程池执行，
不会阻塞事件循环。

**判断标准**：这个接口里有没有 `await`。
- 有（调 LLM、调异步 HTTP）→ `async def`
- 没有（纯 DB / 纯计算）→ `def`，让框架丢线程池

写反了会出问题：
- `async def` 里调同步阻塞代码 → 卡死事件循环
- `def` 里写 `await` → 语法错误

## 四、业务编排：`agent_service`

### 4.1 `stream_answer` 的三段式

文件：`service/agent_service.py`，约 400 行，是整个项目的核心。

```python
async def stream_answer(db, cfg, query, history=None, use_rerank=None,
                        top_k=None, rerank_n=None, direct=False):
    """核心链路，逐段产出事件。"""
    started = time.perf_counter()

    # ---------------- ① 路由 ----------------
    if direct:
        decision = {"intent": "advice", "domain": "all", "rewritten": query,
                    "need_retrieval": False, "by": "direct"}
        yield _status("routed", "直聊模式 · 跳过检索")
    else:
        yield _status("route", "正在理解你的问题…")
        decision = await route(cfg, query, history)
        yield _status("routed", f"识别为{intent_label} · 检索范围：{domain_label}", ...)

    # ---------------- ② 检索 ----------------
    hits = []
    if decision["need_retrieval"]:
        yield _status("retrieve", "正在检索…")
        hits = await asyncio.to_thread(retrieve, db, decision["rewritten"] or query, ...)
        yield {"type": "sources", "sources": to_source_payload(hits)}

    # ---------------- ③ 生成 ----------------
    llm = build_client(cfg)
    yield _status("generate", "正在组织回答…")
    messages = _build_messages(cfg, decision, query, format_context(hits), history)

    async for piece in llm.astream_chat(messages):
        yield {"type": "delta", "text": piece}

    yield {"type": "answer", "answer": ..., "sources": ..., "elapsed_ms": ...}
```

**三个设计要点**：

1. **它是个 async generator，不是普通函数**
   好处：同一个生成器既能喂给 SSE 接口，也能在测试里直接 `async for` 遍历断言，
   不用起 HTTP 服务。

2. **`asyncio.to_thread` 而不是 `fastapi.concurrency.run_in_threadpool`**
   后者能用，但会让 service 层依赖 FastAPI。用标准库的 `to_thread`，
   service 层就是纯 Python，换框架不用改这里。

3. **`direct` 参数**
   前端顶栏那个"直聊"开关。跳过路由和检索，直接生成。
   复用同一个生成器，不用写两套逻辑。

### 4.2 ① 路由：`route()`

```python
async def route(cfg, query, history, allow_llm=True) -> dict:
    # 第一步：规则路由（零成本、毫秒级）
    rule = _rule_route(query)
    if not allow_llm or (rule["intent"] == "statute" and rule["domain"] != "all"):
        return rule          # ← 明确问条号，直接返回，不调 LLM

    # 第二步：LLM 路由
    llm = build_client(cfg)
    try:
        raw = await llm.achat([{"role": "system", "content": ROUTER_SYSTEM},
                               {"role": "user", "content": build_router_user(query, history)}],
                              temperature=0.0, max_tokens=400, timeout=30)
        parsed = _parse_json_block(raw)
        if not parsed:
            return rule      # ← 解析失败，兜底
        return {"intent": intent, "domain": domain, "rewritten": ..., "need_retrieval": ..., "by": "llm"}
    except LLMError:
        return rule          # ← 调用失败，兜底
```

**规则路由长什么样**：

```python
def _rule_route(query: str) -> dict:
    if STATUTE_LOOKUP_PATTERN.search(query) or "《" in query:
        intent = "statute"
    elif domain_scores:
        intent = "advice"
    ...
```

正则抓的是"第X条""第X款"这类明确信号，同时用关键词表给 domain 打分。

💡 **会被问**："LLM 路由挂了怎么办？"

> 三层防御：规则先跑（明确问条号的根本不调 LLM）；LLM 返回解析失败退回规则；
> LLM 调用异常也退回规则。核心原则是 **LLM 是增强项，不是单点依赖** ——
> 模型服务挂了，系统应该降级成"规则路由 + 向量检索"，而不是整个不可用。

### 4.3 ③ 生成：`astream_chat()`

```python
# llm/client.py
async def astream_chat(self, messages, temperature=None, max_tokens=None, timeout=240):
    if max_tokens is None:
        max_tokens = 4096 if self.is_reasoning else 1600   # ← 按模型类型给预算

    async with httpx.AsyncClient(trust_env=False, timeout=timeout) as client:
        async with client.stream("POST", url, headers=..., json=payload) as resp:
            async for line in resp.aiter_lines():
                chunk = self._parse_sse_line(line)
                delta = chunk["choices"][0]["delta"]

                if delta.get("reasoning_content"):
                    reasoning_chars += len(...)     # ← 只计数，不输出

                if piece := delta.get("content"):
                    content_emitted = True
                    yield piece

    if not content_emitted:
        if reasoning_chars:
            yield REASONING_EMPTY_TEMPLATE.format(...)   # ← 给可操作提示，不吐草稿
        else:
            raise LLMError("模型没有返回任何内容")
```

💡 **这是全场最有故事的一段，见第七章详细展开。**

### 4.4 事件类型：前后端的契约

| 事件 | 时机 | 前端怎么用 |
|---|---|---|
| `status` | 每个阶段开始 | 显示"正在检索…"，让用户知道系统在干什么 |
| `sources` | 检索完成、生成之前 | **先渲染法条卡片**，用户不用等生成完才知道查到了什么 |
| `delta` | 每个 token | 打字机效果 |
| `answer` | 生成结束 | 用清洗后的完整文本覆盖 delta 累积的内容 |
| `done` | 落库完成 | 显示总耗时 |
| `error` | 异常 | 红色提示 |

**`sources` 早于 `answer` 是刻意的**：法律问答里"查到了什么"比"说了什么"更能建立信任。

## 五、检索层（最核心，最容易被深挖的部分）

### 5.1 数据怎么进来：`rag/chunker.py`

**核心约定：一个 `###` 小节 = 一个 chunk。**

```python
def parse_markdown(path, domain, chunk_size=420, overlap=60) -> ParsedDoc:
    """返回 chunks（进向量库） + articles（进 MySQL）"""
    ...
    for line in lines:
        if line.startswith("# "):          # 文档标题
        elif line.startswith("## "):       # 章 → 记到 chapter 变量
        elif line.startswith("### "):      # 小节 → flush_section()，开新的 current
        elif line.startswith(">"):         # 引用块 → 元信息（法律名称/简称/领域）
        else:                              # 正文 → 攒进 current["lines"]
```

**两种小节的区别**：

```
### 第十条 【建立劳动关系应当订立书面劳动合同】   ← 是法条 → 进 MySQL + 向量库
条文正文……

### 要点：什么是事实劳动关系                        ← 不是法条 → 只进向量库
解读文字……
```

解析器用正则判断标题是不是"第X条"，是的话额外产出一个 `Article` 对象。

**chunk 的文本长什么样**：

```python
def _prefix(heading_text=""):
    """chunk 的上下文前缀。让向量自己带上出处，是提升法律检索召回最便宜的办法。"""
    parts = []
    if meta.get("law_short"):
        parts.append(f"《{meta['law_short']}》")
    if chapter:
        parts.append(f"{chapter} ")
    ...
    return text + heading_text
```

最终 chunk 的 `text` = `《劳动合同法》二、试用期 第十九条【试用期期限】\n正文……`

💡 **为什么要加这个前缀**（这是设计上的关键点）：

> 向量模型对"短查询 vs 长文档"的匹配天然吃亏。用户问"劳动合同法第十九条"，
> 文档里只有"劳动合同期限三个月以上……"，两者语义距离并不近。
> 拼上出处之后，查询词和文档里出现了同样的关键词和条号，余弦相似度直接上去。
> 这招零成本 —— 不增加 embedding 调用，只多几个字符。

**长文本怎么办**：`_split_long_text(text, chunk_size, overlap)` 按句子边界切，
带 60 字重叠。但**法条本身绝不切**（一条就是一个 chunk）。

### 5.2 怎么入库：`indexer` + `embedder` + `milvus_store`

三个文件各管一段：

| 文件 | 职责 |
|---|---|
| `indexer.py` | 编排：读文件 → 比 sha1 判断要不要重建 → 调 chunker → 写 MySQL 法条表 → 调 embedder → 写 Milvus → 更新台账 |
| `embedder.py` | 把文本批量转成向量（分批 32 条 + 重试 + 进程内缓存） |
| `milvus_store.py` | 集合的建/删/查/写 |

**增量索引的实现**：

```python
# indexer.py
def index_file(path, domain, force=False) -> IndexResult | None:
    fingerprint = file_fingerprint(path)      # sha1(文件内容)
    existing = knowledge_dao.get(db, domain, path.name)
    if existing and existing.fingerprint == fingerprint and not force:
        return None                            # ← 没改过，整段跳过
```

💡 **为什么要指纹**：32 份文档全量重建要 8—12 分钟和一笔 embedding 费用。
改一份文件只重建一份，这是实打实的成本优化。

**Milvus 集合有一个必须知道的坑**：

```python
# milvus_store.py
def ensure_loaded(name: str) -> None:
    """确保集合已加载进内存，可以检索。

    这是 Milvus 最容易踩的一个坑：插入数据、建完索引之后能立刻 search，
    因为集合还在内存里；但进程一重启，集合状态就是 released，
    再 search 会直接抛异常。而且这个异常在 Lite 模式下不会自动恢复，
    必须显式 load 一次。
    """
    if name in _loaded:      # ← 进程内缓存，避免每次检索都多一次 RPC
        return
    client.load_collection(name)
    _loaded.add(name)
```

💡 **这个坑值得展开讲**：它只在"进程重启后"出现，建索引那次不会报，
所以极度容易被误判成"数据没写进去"。

**索引类型用 FLAT**：

```python
index_params.add_index(field_name="vector", index_type="FLAT", metric_type="COSINE")
```

> 几千条数据下，暴力搜索（FLAT）比 HNSW / IVF 更快也更准，还省内存。
> 数据量上到十万级才需要换索引类型，那时只要改建索引参数，代码不用动。

### 5.3 怎么查出来：`retriever.retrieve()` ★★★

**这是整个项目最核心的 120 行，必须逐行看懂。**

```python
def retrieve(db, query, domain=None, top_k=8, rerank_n=4, use_rerank=True, api_key=None):
    query = query.strip()
    if not query:
        return []

    # 先拿到"已知的法律名列表"，给下面的正则匹配用
    known_laws = [item["law_name"] for item in statute_dao.list_laws(db)]
    signals = _detect_structured_signals(query, known_laws)

    candidates = []

    # ═══════ 第 1 路：结构化直查 ═══════
    if signals["article_no"] and signals["law_name"]:
        row = statute_dao.find_by_article(db, signals["law_name"], signals["article_no"])
        if row is None:
            # 用户可能写"第19条"，数据库存的是"第十九条"，转一下再查
            normalized = f"第{_normalize_article_no(inner)}条"
            row = statute_dao.find_by_article(db, signals["law_name"], normalized)

        if row is not None:
            candidates.append({... "score": 1.0, "source": "structured"})

    # ═══════ 第 2 路：向量语义检索 ═══════
    embedder = get_embedder()
    domains = [domain] if domain in LAW_DOMAINS else list(LAW_DOMAINS)

    # 跨域时每个域少取：否则 6 × 8 = 48 条候选，rerank 费用和延迟都上去
    per_domain = top_k if len(domains) == 1 else max(2, top_k // 2)

    vector = embedder.embed_query(query)
    for item in domains:
        hits = milvus_store.search(collection_name(item), vector, top_k=per_domain)
        candidates.extend(hits)

    # ═══════ 第 3 路：词表扩展补召回 ═══════
    expanded = _expand_query(query, domain)      # "加班费" → "延长工作时间 加班工资 …"
    if expanded != query:
        expanded_vector = embedder.embed_query(expanded)
        for item in domains:
            for hit in milvus_store.search(...):
                hit["score"] *= 0.92          # ← 扩展召回打 92 折
                hit["source"] = "expanded"
                candidates.append(hit)

    if not candidates:
        return []

    # ═══════ 融合与重排 ═══════
    merged = _dedupe(candidates)
    # 结构化命中加 0.5 偏置，保证它进候选池
    merged.sort(key=lambda h: h.get("score", 0) + (0.5 if h.get("source") == "structured" else 0),
                reverse=True)
    shortlist = merged[: max(rerank_n * 3, 12)]     # 送进精排的候选

    if use_rerank:
        final = get_reranker(api_key).rerank(query, shortlist, top_n=rerank_n)
    else:
        final = shortlist[:rerank_n]

    # 兜底 1：结构化命中强制置顶
    structured = [c for c in merged if c.get("source") == "structured"]
    if structured:
        wanted = structured[0]
        rest = [item for item in final if not (同一条)]
        final = ([wanted] + rest)[:rerank_n]

    # 兜底 2：保证至少有法条原文，不能全是解读段落
    final = _ensure_article_quota(final, shortlist, rerank_n)

    return final
```

**五个必须能讲的设计点**：

#### ① 为什么要有第 1 路（结构化直查）

> 用户问"劳动合同法第十九条"，答案是唯一的。向量检索能召回第十七、十八、二十条，
> 但未必正好是第十九条。所以走 MySQL 精确查询，100% 准确。

#### ② 为什么第 3 路的分数要打折

> 扩展召回的是"猜你想问"，不是用户原话。如果扩展结果的分数和原始检索一样高，
> 会把真正相关的挤掉。打 92 折是经验值。

#### ③ 去重键为什么是 `(law_name, article_no)` 而不是文本前 N 字

💡 **这是改过的 bug，可以当故事讲**：

> 一开始我按文本前 40 字去重，结果同一条法条出现两遍 ——
> 结构化直查的文本带"《法名》第X条【主旨】"前缀，向量召回存的是纯条文，
> 前缀不同合并不了。改成按 (法律名, 条号) 去重才对。

#### ④ 为什么结构化命中要强制置顶（而不只是加偏置）

> 精排按语义相关性打分，"要点：试用期最长能多久"这种解读段落确实比条文原文更贴题。
> 但用户明确问第X条的时候，他要的是**条文原文本身**，不是我们的解读。
> 这是产品判断压过模型判断的地方。

#### ⑤ `_ensure_article_quota` 为什么从"强约束"改成"兜底"

💡 **这是最有价值的一个故事**：

> 最初写成"解读段落最多 1 条，其余强制给法条原文"，想让模型少看二手信息。
>
> 结果问"离婚时彩礼需要返还吗"时翻车了 —— 彩礼返还规则本来就在司法解释里，
> 我的语料把它写成了「要点」段落；强行换成《民法典》第 1087 条（离婚财产分割）、
> 第 1091 条（离婚损害赔偿）这些"看起来有法条"的内容，
> 反而把真正有用的答案挤掉了，模型只能硬着头皮讲财产分割，完全跑题。
>
> 所以改成了兜底：只在**一条法条原文都没有**时补一条，排序交给 rerank。
> 教训是：**规则不能跟语义相关性抢方向盘**。

### 5.4 精排：`reranker.py`

```python
class Reranker:
    def rerank(self, query, candidates, top_n=4) -> list[dict]:
        if not candidates:
            return []
        if len(candidates) == 1:
            return candidates
        try:
            resp = httpx.post(f"{base}/rerank", json={...}, timeout=20, trust_env=False)
            if resp.status_code != 200:
                return candidates[:top_n]      # ← 降级
            ...
        except Exception:
            return candidates[:top_n]          # ← 降级
```

**三层防御**：候选为空、候选只有 1 条、接口超时/报错。

💡 可能会问："rerank 挂了怎么办？"

> 降级为向量粗排，打 warning 日志，用户无感。精排是锦上添花，不是单点依赖。

### 7.2 推理模型的处理（三个坑，一个比一个深）

💡 **这是最能体现"踩过坑"的一段，建议完整背下来。**

#### 坑一：`content` 为空 ≠ 没有回答

推理模型的响应长这样：

```json
{
  "message": {
    "reasoning_content": "The user is asking... Let me check the materials...
                           Note: I should not fabricate article numbers...
                           Let me draft: 结论：公司安排加班不付加班费是违法的…",
    "content": "**结论**：公司的做法违法，你有权要求补发加班费…"
  }
}
```

`reasoning_content` 是草稿，`content` 才是答案。

**最初写错的兜底**：

```python
# ❌ 错误写法
def _pick_content(message):
    content = message.get("content")
    if content:
        return content
    return message.get("reasoning_content") or ""    # ← 草稿当答案
```

结果用户看到整段英文独白，里面有 "The user is asking"、"Let me draft"、
"注意要控制在500字以内"。

**现在的写法**：

```python
# ✅
def _pick_content(message):
    """只取正式答案，绝不回退到 reasoning_content。"""
    return (message.get("content") or "").strip()
```

#### 坑二：思考过程会吃掉全部 token 预算

实测 `glm-5.3-flash` 回答一个简单法律问题：思考 1000—1300 字符，正文 50 字。
复杂问题思考能到 3000 字符（约 2000 token）。

原来按普通模型定的 `max_tokens=1600`，被思考吃光，`content` 直接是空的。

**现在的处理**：

```python
if max_tokens is None:
    max_tokens = 4096 if self.is_reasoning else 1600
```

#### 坑三：脏数据会自我复制

泄漏的思维链被存进 MySQL，下一轮作为 assistant 历史喂回模型。
模型看到"自己"是这么说话的，继续用英文思考，还开始自我纠正，会话越聊越乱。

**读时过滤**：

```python
# dao/message_dao.py
def _looks_like_reasoning_leak(text: str) -> bool:
    if not text or len(text) < 300:
        return False
    lowered = text.lower()
    if any(marker in lowered for marker in _REASONING_MARKERS):   # "the user is asking" 等
        return True
    # 英文占比超过 40%，正常中文回答不会这么高
    ascii_letters = sum(1 for ch in text if ch.isascii() and ch.isalpha())
    return ascii_letters / len(text) > 0.4
```

在 `recent_for_memory()` 里跳过这类消息。

💡 **为什么用"读时过滤"而不是"改数据库"**：

> 已经污染的记录前端仍能展示，用户自己能看见发生了什么；但不会再喂给模型。
> 批量改数据库风险大，而且判断逻辑本身是启发式的，可能误伤。

### 7.3 三套提示词

`llm/prompts.py`：

| 提示词 | 用在哪 | 关键约束 |
|---|---|---|
| `ROUTER_SYSTEM` | 意图路由 | 只输出 JSON，snake_case 字段 |
| `LEGAL_QA_SYSTEM` | 有检索结果时 | 必须依据资料、条号严格对应、不许编 |
| `LEGAL_QA_NO_CONTEXT_SYSTEM` | 没检索到 / 直聊时 | 明说"未收录"，别硬凑 |
| `CHITCHAT_SYSTEM` | 闲聊 | 简短回应 |

`LEGAL_QA_SYSTEM` 里最关键的三条：

```
2. 注意每段资料开头的类型标签：条文原文 / 解读（非条文原文）
3. 条号与内容必须严格对应，绝不把 A 条的内容归到 B 条名下
5. 引用要克制，不要把不相干的条文硬套到问题上
```

💡 **第 3 条是怎么来的**：

> 实测模型会把"试用期最长六个月"这段解读，说成是《劳动合同法》第二十条的规定 ——
> 第二十条其实讲的是试用期工资。它看到上下文里有第二十条，就"就近归因"了。
> 所以我给上下文每段加了类型标签，并明确要求条号严格对应。

### 8.2 SSE 解析：`api/stream.js`

**为什么不用 axios**：axios 基于 XHR，拿不到"边下边读"的增量数据。
只有 `fetch` + `ReadableStream` 才行。

```javascript
const reader = response.body.getReader()
const decoder = new TextDecoder()
let buffer = ''

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })    // ← stream: true 处理半个汉字
  const frames = buffer.split('\n\n')
  buffer = frames.pop()                                 // ← 最后一段可能不完整，留到下次
  for (const frame of frames) {
    if (frame.startsWith('data:')) onEvent(JSON.parse(frame.slice(5)))
  }
}
```

💡 **三个细节**：

1. `decoder.decode(value, { stream: true })` —— 处理多字节汉字被切断在 chunk 边界
2. 按 `\n\n` 切帧，不是按行
3. `buffer = frames.pop()` —— 最后一段可能不完整，留到下次拼接
