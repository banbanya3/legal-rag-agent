# 法律知识库说明

这份文档说明 `knowledge_base/` 里 32 份文档的组织方式、编写约定、以及怎么往里加内容。

### 语料来源

- 法律条文以全国人大及其常委会公布的现行文本为准，参考中国政府网、国家法律法规数据库的公开内容整理。
- 司法解释、部门规章的要点参考最高人民法院、最高人民检察院的公开文件。
- 每份文档里的「要点」「实务问答」部分是整理者的归纳，不是条文原文 —— 这一点在文档里、也在检索上下文的类型标签里都做了明确区分。

### 已知的时效风险

法律会修订。这份语料覆盖的是编写时（2026 年）有效的版本，但：

- 刑法已经过十二个修正案，本文档只覆盖了总则和几类常见罪名，未逐条同步修正案；
- 民法典的司法解释在持续出台（如 2024 年的彩礼纠纷规定），文档中以「要点」形式吸收，未逐条对应条文；
- 地方性法规（如各地养犬管理条例、物业管理条例）未收录。

**生产环境应该做的事**：接入国家法律法规数据库的开放数据，建立增量同步任务；在法条表加 `invalid_date` / `version` 字段，回答时对已修订条文做提示。

## 二、文档结构约定

解析器（`backend/rag/chunker.py`）依赖固定结构提取法条，格式写错会导致法条进不了 MySQL 表。
新增文档时严格按下面的模板。

### 2.1 文件头：元信息块

```markdown
# 《中华人民共和国劳动合同法》核心条文与实务要点

> 法律名称：中华人民共和国劳动合同法
> 简称：劳动合同法
> 施行日期：2008-01-01
> 最近修正：2012-12-28
> 领域：labor
> 标签：书面劳动合同, 试用期, 经济补偿
```

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 法律名称 | 是 | 全称，写进 MySQL `statute_article.law_name` |
| 简称 | 是 | 展示用，写进 chunk 前缀，直接影响召回 |
| 施行日期 | 否 | 展示用 |
| 最近修正 | 否 | 展示用 |
| 领域 | 是 | 六个 key 之一，与目录对应 |
| 标签 | 否 | 检索辅助，暂未参与计算 |

**必须放在文件最前面**，且在任何 `###` 标题之前 —— 解析器只在"还没解析出法条"时读取元信息。

### 2.2 章节：二级标题

```markdown
## 一、劳动合同的订立
```

`##` 会被记为"当前章"，写进后续所有 chunk 的前缀（如 `《劳动合同法》二、试用期 第十条…`）。
这能提升"试用期相关的条文"这类按主题检索的命中率。

### 2.3 法条：三级标题 + 条号

```markdown
### 第十条 【建立劳动关系应当订立书面劳动合同】

建立劳动关系，应当订立书面劳动合同。

已建立劳动关系，未同时订立书面劳动合同的，应当自用工之日起一个月内订立书面劳动合同。
```

规则：

- 必须是 `### 第X条` 开头，X 支持中文数字和阿拉伯数字；
- 方括号里的主旨可选，但强烈建议写 —— 它是检索时的重要信号；
- 条文正文到下一个 `###` 或 `##` 结束，中间可以有空行、多段；
- 一条法条会被同时写进 Milvus（一个 chunk）和 MySQL（一行记录）。

### 2.4 解读段落：三级标题 + 非条号标题

```markdown
### 要点：什么是事实劳动关系

没有书面合同，但同时具备下列情形的，劳动关系成立……
```

只要 `###` 后面不是"第X条"，就当普通小节处理：**只进向量库，不进法条表**。
建议用「要点：」「实务问答：」「案例：」开头，检索时这些标题会作为 chunk 前缀。

### 2.5 引用块

`> 开头`的行，如果在文件头部且 key 在元信息白名单里，当元信息；
否则剥掉 `>` 后当正文。

## 三、怎么写才有好的检索效果

这是写完 32 份文档后总结的几条经验，比格式本身更重要。

### 3.1 条号前缀要完整

`### 第十条 【建立劳动关系应当订立书面劳动合同】` 比 `### 第十条` 好得多。
主旨短句是用户最常用的查询词（"试用期期限""经济补偿标准"），把它写进标题，
等于给这条法条加了人工标注的关键词。

### 3.2 一条法条只写一条

不要把"第十条、第十一条、第十二条"塞进同一个 `###` 小节。
一条法条一个 chunk 是整套检索的基础，合并会让条号定位失效。

### 3.3 解读要写成"能独立看懂"的一段

切片是按 `###` 切的，读者（模型）看不到上下文。所以每个「要点」小节要自洽：

- 主语写全（不要写"该条""上述规定"，直接写"《劳动合同法》第十九条"）；
- 结论前置（第一句就是答案，后面再解释）；
- 300—600 字为宜，超过会被二次切分，可能切断逻辑。

### 3.4 数字和期限写清楚

法律问答里最高频的就是"多久""多少"。写成"六个月""百分之八十""三倍"，
不要写"较长""相应比例"。模型会照抄这些表述。

### 3.5 别把司法解释写成条文

司法解释没有"第X条"的条号体系（有，但不是民法典的条号）。这类内容一律写成
「要点：」，并且在正文里说明"这是最高人民法院《关于……的规定》"。
否则模型会把它当成某条民法典条文引用 —— 这是我在测试中真实踩到的坑。

## 四、如何扩充知识库

### 4.1 加一份新文档

1. 在对应领域的目录下新建 `.md`，按上面的模板写；
2. 只重建这一个领域：

```bash
cd backend
python init_knowledge.py --domain labor --build
```

增量逻辑会比对文件 sha1，已索引且未改动的文件直接跳过，只处理新的这一份。

### 4.2 加一个新领域

改 `backend/config.py` 的 `LAW_DOMAINS`，加一项：

```python
"admin": {
    "label": "行政与许可",
    "dir": "07_admin",
    "desc": "行政许可、行政强制、政府信息公开、信访",
    "tool": "检索行政许可、行政强制、信息公开等问题",
    "color": "#0e7490",
},
```

然后建目录、放文档、`python init_knowledge.py --domain admin --build`。
API、前端知识库页面、统计页会自动多出这一个领域 —— 领域注册表是唯一真相源。

### 4.3 上传自定义资料

前端的「知识库 → 上传我的法律资料」支持 `.txt` / `.md`。
上传的文件进独立的 `law_upload` 集合，和内置法律库物理隔离：

- 不会因为重建内置库被冲掉；
- 不会污染法条表（上传文件没有规范结构，强行解析只产生脏数据）；
- 删除时只删自己那份。

### 4.4 彻底重建

```bash
python init_knowledge.py --reset      # 清空向量与法条表（源文件不动）
python init_knowledge.py --build --force
```

`--force` 会先 `drop_collection` 再重建，用在改了 `CHUNK_SIZE`、
换了 embedding 模型（维度变了）这类场景。

## 五、维护检查清单

改完知识库后，建议按顺序过一遍：

1. `python init_knowledge.py --check` —— 环境与文件数量体检
2. `python init_knowledge.py --build` —— 看每个领域的切片数、法条数是否符合预期
3. 打开前端「法条检索」，搜一个刚加的关键词，确认条文能查到
4. 在对话里问一个相关问题，看「引用的法条」卡片里有没有新内容
5. 检查法条数：`SELECT count(*) FROM statute_article;` 应该等于各文档法条数之和接口输出的条数

如果第 3 步查不到但第 2 步数字正常，通常是 `### 第X条` 的格式写错了
（比如用了 `####`、或者条号里混了空格）。
